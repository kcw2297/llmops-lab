# ocr-extraction

## 개념 (백엔드 비유)
- **문서 추출** = 이미지를 받아 스키마가 고정된 JSON을 돌려주는 API. 채팅이 아니다. 대화 이력, tool calling, RAG를 쓰지 않는다.
- **이미지 토큰** = 이미지를 잘게 나눈 조각이 텍스트 토큰처럼 컨텍스트를 차지한다. 해상도를 올리면 작은 글씨를 잘 읽지만 토큰·VRAM·지연이 늘어난다. 업로드 파일 크기 제한과 비슷한 트레이드오프다.
- **구조화 출력(guided decoding)** = 서버가 JSON Schema에 맞지 않는 토큰을 생성 단계에서 막는 것. 응답 바디를 스키마로 검증하는 것보다 한 단계 앞이다. 형식은 보장하지만 **값이 맞는지는 보장하지 않는다.**
- **필드 정답률** = 단위 테스트의 assert 통과율. 문서 완전 일치율은 "모든 assert가 통과한 테스트 케이스 비율"이다.

## 절차
1. **문서·필드 정의**: 양식별로 추출할 필드와 타입을 정한다(앱 레포 2단계 기획서 3절 기준). 금액은 정수(원), 날짜는 `YYYY-MM-DD`, 없는 값은 `null`로 정규화 규칙을 먼저 정한다.
2. **스키마와 프롬프트**: 양식마다 JSON Schema 1개와 짧은 지시문을 둔다. 프롬프트에 "문서에 없는 값은 null, 계산하지 말 것"을 넣는다.
3. **호출**: `POST /v1/chat/completions`에 이미지(`image_url`, base64 data URL)와 지시문을 넣고, `response_format={"type":"json_schema", ...}`로 구조화 출력을 켠다. `temperature=0`.
4. **해상도**: 모델이 허용하는 이미지 토큰 예산(최대 픽셀, 비전 토큰 수)을 config에 명시한다. 같은 실험 안에서는 고정하고, 바꿀 때는 별도 실험으로 비교한다.
5. **전자 PDF 먼저 거르기**: 글자 레이어가 있는 PDF는 텍스트 추출로 충분한지 먼저 본다. 모델이 필요한 문서만 VLM으로 보낸다(앱 기획 E0).
6. **데이터셋**: `eval/datasets/{name}-v{n}/`에 이미지와 정답 JSON을 짝지어 둔다. 실문서는 쓰지 않고 템플릿으로 합성하거나 가명 처리한다. 데이터 카드(README)에 생성 방법, 건수, 양식 목록을 적는다. 수정하면 버전을 올린다.
7. **채점**: 필드별로 정규화한 뒤 정확히 일치하는지 비교한다. 금액·날짜·계좌번호는 부분 점수 없이 일치/불일치만 센다. JSON 파싱 실패도 별도로 센다.
8. **실패 분류**: 누락, 오독(숫자·한글), 환각(문서에 없는 값), 형식 오류, 표 행 밀림으로 나눠 센다.

## 코드 규칙
- 위치: 추출·채점 코드는 `eval/src/ocr_eval/`, 실행 설정은 `eval/configs/{suite}.yaml`
- 설정: `.env`의 `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`
- 의존 규칙: `ocr_eval`은 `ocr_core`만 import한다. 앱 레포 코드는 import하지 않고, 앱도 이 레포를 import하지 않는다
- 결과 원본(필드별 예측·정답 CSV/JSONL): `artifacts/experiments/{id}/results/`

## 흔한 실패 패턴 (발견하면 learning-note에 기록)
- 콤마·자릿수가 많은 금액을 잘못 읽음, 표에서 행이 하나씩 밀림, 비슷한 한글 글자를 바꿔 읽음
- 문서에 없는 값을 그럴듯하게 채움(환각), 합계를 직접 계산해서 씀
- 해상도가 낮아 작은 글씨를 놓침, 해상도가 높아 컨텍스트 초과·OOM
