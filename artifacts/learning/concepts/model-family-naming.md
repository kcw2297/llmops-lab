# 모델 패밀리와 이름 읽는 법 (Qwen 예시)

## 한 줄 정의
오픈소스 모델 이름은 `{패밀리}{세대}-{모달리티}-{크기}-{학습 단계}-{양자화}` 조각의 조합이고, 같은 "Qwen"이라도 조각마다 다른 모델(다른 가중치 파일)이다.

## 백엔드/DevOps로 치면
- **세대(Qwen2.5 → Qwen3 → Qwen3.5)** = 메이저 버전. 아키텍처와 학습 데이터가 바뀐다. 서빙 엔진(vLLM)의 지원 버전도 따로 확인해야 한다(새 런타임 버전에 맞는 드라이버가 필요한 것과 비슷).
- **크기(0.8B, 9B, 27B …)** = 인스턴스 타입. 같은 API를 주지만 필요한 메모리와 성능이 다르다.
- **Base / Instruct / Thinking** = 같은 코드의 빌드 프로파일. Base는 "다음 단어 예측"만 배운 원본, Instruct는 지시를 따르게 추가 학습한 것, Thinking은 답 전에 추론 과정을 길게 쓰도록 학습한 것.
- **Dense / MoE(`A17B`)** = 모놀리스 vs 요청마다 일부 서비스만 깨우는 라우팅 구조. `397B-A17B`는 전체 397B 중 토큰당 17B만 계산한다. **단, 메모리에는 397B 전부를 올려야 한다**(배포 이미지는 전체 크기).
- **양자화 접미사(AWQ, GPTQ, FP8, GGUF)** = 같은 바이너리를 압축한 배포판. 용량과 속도는 좋아지고 정확도는 조금 손해 본다.

비유의 한계: 소프트웨어 버전업은 하위 호환을 지키려 하지만, 모델은 세대가 바뀌면 같은 프롬프트에도 출력이 달라진다. 버전을 올리면 평가를 다시 돌려야 한다.

## 실제로는 어떻게 동작하나
Qwen 계열 중 이 프로젝트와 관련 있는 줄기 (2026-11 기준):

```
Qwen2.5-VL (2025 초)        이미지 입력 가능한 별도 VL 라인
   │
Qwen3 (텍스트) + Qwen3-VL (2025 하반기, 2B~235B, Apache 2.0)
   │                         └ 텍스트 모델에 비전 인코더를 붙인 구조. 파인튜닝 사례가 가장 많음
   ▼
Qwen3.5 (2026-02~)           텍스트·이미지를 처음부터 함께 학습(native multimodal)
   ├ 397B-A17B, 122B-A10B, 35B-A3B   (MoE)
   └ 27B, 9B, 4B, 2B, 0.8B            (Dense)
```

HF 저장소 이름 예: `Qwen/Qwen3-VL-8B-Instruct` → 패밀리 Qwen, 세대 3, VL 라인, 8B Dense, Instruct.

크기 → VRAM 감 (가중치만, bf16 = 파라미터 × 2바이트):
- 9B ≈ 18GB, 4B ≈ 8GB, 27B ≈ 54GB, 35B-A3B ≈ 70GB (활성 3B여도 전체를 올림)

## 내 실험에서 본 것
아직 없음. M1(VLM 후보 비교)에서 후보별 실제 VRAM 사용량, 이미지 1장 `prompt_tokens`, 필드 정답률을 여기에 채운다.

## 흔한 오해
- "Qwen = 모델 하나" → 수십 개 가중치의 묶음이다. 실험 기록에는 반드시 전체 repo 이름과 revision을 적는다.
- "MoE의 활성 파라미터만큼 메모리가 든다" → 계산량만 줄고 메모리는 전체 크기가 필요하다.
- "최신 세대가 항상 낫다" → 새 세대는 벤치마크는 높아도 서빙 엔진·LoRA 도구 지원과 사례가 아직 적을 수 있다. 우리 양식 평가 세트로 확인한다.
- "Thinking 모델이 추출에 더 좋다" → 문서 필드 추출은 추론보다 정확히 읽기가 중요하다. 생각 토큰만큼 지연과 비용이 늘어난다. 추출에는 Instruct(또는 thinking 끔)가 기본이다.

1. `Qwen3.5-35B-A3B`를 bf16으로 올리려면 가중치만 대략 몇 GB가 필요한가?
2. 문서 필드 추출용으로 Base, Instruct, Thinking 중 무엇을 고르고, 왜 그런가?
3. 세대를 Qwen3-VL에서 Qwen3.5로 바꿀 때 서빙 쪽에서 먼저 확인할 두 가지는?

<details><summary>답</summary>

1. 약 70GB. 활성 3B는 계산량이고, 메모리에는 35B 전부를 올린다.
2. Instruct. 지시와 JSON 형식을 따르도록 학습되어 있고, Thinking은 추론 토큰 때문에 지연·비용이 늘지만 "정확히 읽기"에는 이득이 작다. Base는 지시를 잘 따르지 않는다.
3. 사용하는 vLLM 버전이 그 아키텍처를 지원하는지, 그리고 (M4 대비) vLLM에서 해당 모델의 LoRA 어댑터 서빙을 지원하는지.
